# SupportPilot Principles

These principles define how SupportPilot should evolve over time.

Every new feature, workflow, interface, and architectural decision should reinforce these principles.

If a proposed feature violates one or more of these principles, reconsider the design before implementing it.

---

# 1. Solve the user's problem.

Every feature must exist to solve a real problem.

Avoid adding functionality simply because it is technically possible.

---

# 2. Guide, don't overwhelm.

SupportPilot should reduce complexity.

Users should always know what to do next.

Break difficult troubleshooting into small, understandable steps.

---

# 3. Earn trust.

Users should be able to trust every recommendation.

Information should be technically accurate, reviewed when appropriate, and transparent about uncertainty.

Trust is the product.

---

# 4. AI assists. Humans decide.

Artificial intelligence should accelerate work, not replace judgment.

AI generates.

Humans review.

SupportPilot publishes.

---

# 5. One source of truth.

Knowledge should exist in one place.

Avoid duplicate articles, duplicate workflows, and conflicting documentation.

Every published article should become the canonical reference.

---

# 6. Consistency beats cleverness.

Users should not have to relearn the interface.

Buttons, navigation, layouts, terminology, and workflows should behave consistently throughout the platform.

---

# 7. Every click should have purpose.

Avoid unnecessary pages, dialogs, confirmations, and navigation.

Each interaction should move the user closer to solving their problem.

---

# 8. Build for growth.

SupportPilot should grow naturally.

New workflows, operating systems, vendors, AI providers, and learning experiences should integrate without requiring major architectural changes.

Design today for capabilities that may not exist yet.

---

# 9. Knowledge is a product.

Articles are not temporary content.

Published knowledge should be reviewed, versioned, maintained, and treated as long-term assets.

---

# 10. Learning should happen naturally.

SupportPilot should not simply provide answers.

Whenever appropriate, it should explain why a step matters so users become more capable over time.

---

# 11. Official documentation comes first.

When external references are provided, prioritize vendor documentation whenever practical.

Users should arrive on pages that immediately support the current topic instead of forcing unnecessary navigation.

---

# 12. Simplicity is a feature.

Simple systems are easier to understand, maintain, and trust.

Avoid unnecessary complexity.

---

# 13. Professional by default.

SupportPilot should feel calm, deliberate, and dependable.

Avoid gimmicks, excessive animation, unnecessary notifications, and distracting interface elements.

---

# 14. Design for durability.

Technology changes.

SupportPilot should be built to evolve without frequent redesign.

Favor reusable components, flexible data structures, and maintainable architecture over short-term convenience.

Every decision should consider how well it will age.

---

# 15. Never sacrifice trust for convenience.

SupportPilot should never hide uncertainty.

If information is incomplete, outdated, or AI-generated, users should know.

Trust takes years to earn and seconds to lose.

---

# Definition of Done

A feature is not finished because it works.

It is finished when it:

- Solves a real user problem.
- Fits naturally into the existing experience.
- Follows these principles.
- Can be maintained in the future.
- Makes SupportPilot better than it was before.
